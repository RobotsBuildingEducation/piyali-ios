# Original Tutor reply replay

Tutor replay previously requested fresh narration for every reply and disabled replay on every history row at once. Native now checks for that response's original recording first. Only a cache miss uses the web source's visible-text, role, language-tag and preferred-voice rules. In the current Gemini profile its canonical voice name is outside the realtime TTS voice set, so that fallback uses `ash`; the OpenAI profile retains its normalized `marin`/`cedar` choice.

The Gemini transport collects PCM from completed native playback buffers under the same response ID as the visible message. IDs stay unique across the four-turn socket reset. Canceled, paused and ended turns retain the played prefix; pause/end keep the partial visible reply attached to its real response ID. An overflow is discarded rather than presenting an incomplete recording as a complete clip. Local WAV wrapping preserves PCM bytes, pauses, voice and prosody without the narration cache's trimming or resampling. Encoding differs from the browser's MediaRecorder/Opus container.

Recordings live in a bounded, protected local cache keyed by account, target language, support language and response ID. They neither enter learner progress/cloud receipts nor award XP. A fresh visible Tutor session still keeps previous messages private; the presence of cached audio does not populate history. Storage is optional and expires after seven days. A cache read or corrupt entry can fall back to narration. An existing clip that fails playback clears replay state instead of silently requesting a new generation, matching the source's branch order.

Replay ownership covers the asynchronous cache lookup as well as playback. Changing replies, leaving the view, pausing, ending, changing account/languages or starting another narration cancels the old owner. Late lookups/player callbacks cannot start audio or finish a newer owner. The existing live mute choice survives temporary replay ducking. Recorded playback and receive-only narration share native audio-session ownership with Gemini, so closing replay does not deactivate an active Tutor player. Busy state belongs to the replayed message; other replies remain available.

## Source and verification

`node scripts/export-tutor-replay.mjs` reads the original `playSavedClip`/`stopReplayAudio` and visible-text, voice and language helpers. It executes the actual async source functions with only cache/media I/O stubbed, exports nine branch traces and 32 fallback cases, and records source/runtime hashes in `docs/reference/tutor-replay-source-manifest.json`. Native platform adapters are tested separately; executing a helper is not evidence of full-screen design parity.

The first build compiled but failed to launch the QA app with Mach error -308 and produced no finalized result bundle. `PiyaliTutorReplay2.xcresult` retains 48 passing tests and two failed cases: three assertions incorrectly expected no microphone-restore callback for a missing/user/empty message, and the history UI test selected an underlying, non-hittable button. It also passes all 25 existing/new Tutor session checks (166.805s), eight Gemini transport checks (4.527s), six narration-cache checks (1.626s), two narration-controller checks (0.158s), and both normal long-reply product journeys (58.115s Arabic, 54.643s English). These passing cases do not make that overall run green.

`PiyaliTutorReplay3.xcresult` passes all 26 corrected replay, transport, connection-pool and pause/end checks (14.858s), including the original 32 fallback cases and nine trace branches. Its UI case hits the resume transition before the End control becomes hittable (45.380s); the final UI check waits for the actual live state. `PiyaliTutorReplayFlows4.xcresult` passes the complete replay product journey (88.058s). All four published capture hashes match, and the active, paused, history and private-relaunch states were visually reviewed. The final `PiyaliTutorReplayFinal6.xcresult` passes all 25 checks without failures or skips: 24 replay/transport/narration checks (7.622s), including both audio-session closing orders, and the complete product journey again (84.670s). Its four final published capture hashes match, and every state was visually reviewed. The final `PiyaliTutorReplayLive7.xcresult` passes both live-provider checks without failures or skips: original learner Gemini welcome/capture/disk/replay plus Settings preview (34.403s), and prepared receive-only narration/voice change/cached replay (12.953s). The welcome supplied 438,242 PCM bytes in 37 native played buffers; all recording bytes survived WAV storage and disk reload. Native replay completed without another speech request. Both disposable Firebase identities were deleted and their local keys disconnected. The earlier Live5 checks also pass (30.384s/15.549s) before the final replay-session lifetime refinement. The new product journey uses the normal signup, Start learning, product menu and Tutor controls with explicit isolated offline identity/provider fixtures. Its saved six-second synthetic tone exercises actual local storage and AVAudioPlayer; it does not establish provider speech quality or physical microphone behavior. The live-provider check uses a separate disposable Firebase identity, the original source welcome and real native PCM, without progress writes.

## Remaining

The optional OpenAI full-duplex Tutor transport still lacks original output capture and takes the source cache-miss narration branch. Gemini capture currently commits complete played buffers, so cancellation can omit the already-heard portion of the buffer in flight. Browser silence-tail timing, gain changes within a scheduled buffer, Bluetooth/route interruptions, background recovery and real-device microphone/replay quality need further work. Full Tutor viewport/history-shell/motion, broader languages/text sizes and the other items in `PARITY_AUDIT.md` remain open. This checkpoint does not establish complete functional or design parity.
