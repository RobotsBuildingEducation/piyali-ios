# Authored Game Review completion and replay

The native recap previously separated the epilogue and score into the wrong groups, omitted empty star outlines, used a different wave-bar surface and stretched its card across the screen. The shared native recap follows the original RPG component's authored-completion block: title, target/support epilogue, three outlined star slots, grouped score/wave bar and the completion owner's action. Card width follows its content within the source's 400-point maximum and 16-point phone margins. English/light and Arabic/dark comparisons use the actual prepared chapter at two phone sizes and three scores, including the source fallback title.

The introductory adventure has a separate exit contract. The original RPG component automatically invokes the introduction's skip/advance callback after its final task and hides completion actions. Native now advances the inline six-activity introduction without requiring an extra Continue tap. An unacknowledged completed adventure remains resumable; after the introduction's completion receipt is accepted, reviewing it starts a fresh game. Intro acknowledgment cannot retire the Tutor's own completed game. Tutor keeps its explicit completion action and existing durable acknowledgment/retry flow.

The full product run also exposes a completion-order race: a review that reaches the daily goal releases its celebration before the course queues its lesson acknowledgment, and that celebration blocks the bonus dialog. The original App defers daily-goal release around `awardXp` and releases it from `handleCloseCompletionModal`. Native now validates the review claim on a value copy, queues its lesson presentation before publishing XP, and keeps that presentation identity through the game dismissal. The conductor defers that queued daily goal until the lesson acknowledgment closes; ordinary practice can still celebrate during an unfinished lesson.

Ordinary Game Review completion still owns its original single lesson receipt. A replay can earn a different score and star count without adding another lesson reward, replacing that first receipt or replaying the daily-goal celebration. Preparation, cancellation and process resume keep their existing scope and persistence fences.

## Source boundary

The [source manifest](reference/rpg-completion-source-manifest.json) pins the original RPG component, theme, CSS, WaveBar, scoring profile and bidi utilities. `scripts/reference-rpg-completion.mjs` extracts the original completion JSX, color declarations and localized UI copy. It supplies only a public scenario/score and records the original Continue callback. The source's theme, CSS, native system font selection, WaveBar and bidi helpers execute normally. Both renderers use the same neutral backdrop so this comparison evaluates the recap; maps, gameplay transitions, provider behavior and physical audio are outside that component comparison.

[Paired captures and computed source metrics](reference/rpg-completion-comparison-captures.json) cover 375×667 and 402×874, English/light and Arabic/dark, scores 0, 700 and 800. [Product captures](reference/rpg-completion-product-captures.json) retain the actual native entry/onboarding, authored chapter, pending speech cancellation, saved-game resume, lesson reward, daily-goal celebration, offline cached full replay and relaunch. The public provider fixtures require an explicitly isolated QA identity and do not prefill learner progress.

## Validation

The final production renderer in run 5 passes all seven selected app checks in **68.032s**: twelve source/native recap cases and measured text bounds (**48.491s**), queued reward/daily-goal ownership and unchanged first receipt after a two-star replay (**3.065s**), introduction acknowledgment/fresh replay (**2.662s**), earned recap through the trial boundary (**9.519s**), Tutor completion/review/next lesson (**4.059s**), and both existing daily-goal/Tutor sequencing cases (**0.237s**). The 36 committed component image/metric records come from that passing app selection. Manual review inspects every English and Arabic pair; fine glyph/shadow differences and transition timing remain outside a pixel-equality claim. Its containing result is not all-green because of the UI movement timeout described below. Initial `PiyaliRPGCompletion1.xcresult` passes three checks in 59.440 seconds, including all 12 original/native component cases in 47.178 seconds and introduction acknowledgment/fresh-review ownership in 2.774 seconds. Image review catches the initial full-width native card and different star font/color despite those passing state/callback assertions; its images are superseded by the calibrated run, not evidence of visual parity.

`PiyaliRPGCompletionFlows2.xcresult` completes the full authored introductory adventure in **284.119s**, including automatic final-task exit and the single +50 introductory bonus. Its containing run is intentionally interrupted before the ordinary review journey completes so visual calibration can be applied first; it is not reported as an all-green run. Run 3 passes the introduction-state and earned-recap/quota checks but fails the stricter source geometry comparison: fractional card-width rounding wraps a 21-point epilogue into two lines at 402 points. Native rounds the measured natural text width upward before adding the original padding/border. The test tolerance is unchanged.

Run 4 passes all five selected app checks in **63.919s**, including the 12 source/native geometry cases in **46.532s**, but the ordinary product journey fails waiting for the bonus dialog (**389.615s**). Its accessibility hierarchy shows the +30 recorded on the path and a daily-goal dialog already visible. This is a real presentation-order defect, not a passing complete journey. The subsequent claim/presentation ordering changes address it.

Run 5's UI selection stops at a map movement timeout (**152.690s**) before reaching the reward claim. Run 6 passes that point but fails to find the resumed game after Start (**242.482s**). Their precise causes are not established by those captures. Run 7's new diagnostic screenshot/hierarchy conclusively shows a local progress-write failure because the simulator Data volume is out of space (**189.310s**), with the app's error alert covering the path. That is storage failure, not proof of a camera or preview-transition defect. A speculative 0.2-second camera wait is removed; only failure screenshots/hierarchy are retained in the driver. Redundant task-generated attachment exports are removed, recovering roughly 2.5 GB while retaining every source xcresult bundle and committed capture. Run 8 repeats the strict product journey with the original movement timing after space is recovered.

The final product result, **`PiyaliRPGCompletionFlows8.xcresult`**, passes the complete ordinary journey in **645.527s** with the original movement timing. It covers normal account creation/onboarding/placement, full seven-task prepared play, cancelling an unreturned speech grade, retry, Back/process resume at 3/7, the 100% recap, one +30 lesson acknowledgment before the daily-goal celebration, provider-disabled cached fresh 0/7 replay, all seven replay tasks with three deliberate first-task misses, the 88%/two-star recap, no duplicate reward/celebration, and path/30-XP restoration after another relaunch. All nine final product captures are inspected and their hashes verified. The source/native component captures retain run 5 provenance; production code is unchanged between those checks and run 8.

The expanded Core receipt/persistence check passes in **2.984s**: a new replay with score 700 would ordinarily earn 22 XP, but after the first 800-score/30-XP completion it earns zero, keeps the first receipt's exact encoded bytes, and restores the claimed 700-score practice run with total XP still 30.
