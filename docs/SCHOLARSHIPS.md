# Scholarship prompt and automatic support

The native product now connects the source `BitcoinSupportModal.jsx` to introductory lesson and starter Tutor completion. It shares the Account wallet, its canonical recipient, and its saved monetary recovery state. This checkpoint is part of the wider parity correction; it does not complete that goal.

## Sequence and account state

The six-activity introduction queues the prompt only after earning its first completion. The starter Tutor queues it after its completion and review chain. Existing daily-goal celebrations finish first; queued daily quest/plate celebrations wait until the scholarship prompt closes. The prompt waits for active lesson, completion, review, placement, timer, settings and other blocking surfaces rather than covering their controls. A 160 ms native settle delay follows the preceding overlay.

The source `tutorialBitcoinModalShown` flag is account-wide. Maybe later, Done and Close each dismiss the prompt and queue that canonical setting through the existing offline settings outbox. Practice-language/account changes fence late presentations. Replaying an already completed introduction does not queue another prompt. Closing and reopening the app retains the acknowledged local choice; Firebase synchronization preserves the flag across devices. The root trial gate retains this earned UI sequence until dismissal without changing paid provider grants or permitting new AI activity.

## Automatic one-sat support

A modern native wallet with no saved automatic-support preference adopts the source's default: one sat for each newly earned XP activity while funded, using the canonical recipient or the original Robots Building Education fallback. It does not create a wallet or invoice automatically. The source-managed default permits **zero additional mint fees**. The default mint's active sat keyset reported `input_fee_ppk: 0` in a read-only metadata request on 2026-10-26. A higher fee pauses transfers until the user checks/approves it in Payment tools and recovery. That ceiling is a native adaptation; the web sender does not expose the same approval control.

The existing per-account Keychain preference is authoritative: an explicit Stop, a paused receiving/fee setup, or a manually approved recipient/fee is not overwritten on launch or refresh. Selecting a new source recipient updates future source-managed intents with the zero-fee ceiling. A previously submitted operation keeps its original recipient, inputs and recovery data until it is reconciled; other queued old-recipient intents are canceled. Existing manual-mode selection behavior remains an explicit stop.

The financial intent journal remains separate from the learner snapshot and wallet operation. Positive `PracticeChange` IDs deduplicate through retries and relaunch; unfunded activity does not become future debt. The adoption timestamp excludes historical pending learner events during startup recovery. Actual processing still requires verified recipient receiving information, mint compatibility and proof checks. No unverified main-identity-key fallback is introduced. See [NIP-61](https://github.com/nostr-protocol/nips/blob/master/61.md), [NUT-09 recovery](https://github.com/cashubtc/nuts/blob/main/09.md) and [NUT-02 fees](https://github.com/cashubtc/nuts/blob/main/02.md).
