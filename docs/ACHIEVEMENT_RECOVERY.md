# Achievement sync recovery

The previous native path attempted achievement restoration/publication once and could stop relay publication when its Firebase import failed. The main web product keeps separate cloud and relay retry jobs. The native app now follows those job rules: intent is saved before starting, retries back off from one second to sixty seconds, work is serialized per destination, and an older successful request cannot acknowledge a newer generation. Startup and foreground activation reconcile both channels even when their saved intent is clear. Backgrounding and account changes pause future retries; account guards reject late imports and save results.

`AchievementRetry` implements the source state machine. `AchievementRetryController` owns independent native tasks and twelve-second deadlines, with an atomic, protected intent file per account under Application Support/Piyali/AchievementSync. File names hash the account identifier; files hold only cloud/relay pending flags. Actual progress, awards and operation receipts remain in the existing learner profile/canonical Firebase documents. A malformed or unwritable intent file retains work in memory; a fresh activation always reconciles. Intent-file failure is distinct from losing an award/profile copy, matching the source's exclusion of intent keys from its record-storage warning.

The cloud worker imports restored signed awards through the existing catalog/owner-checked service, then saves the existing progress outboxes. Normal debounced saves and explicit sync join this worker. Stable receipt IDs and the existing transaction verifier retain their ownership of XP, completions and awards. The relay worker restores and saves records locally, then publishes only when the learner's existing sharing preference permits it or an explicitly authorized Publish action requests it. A failed cloud import no longer blocks that relay operation. Restored records are retried into Firebase independently. New collections arriving during a request keep the channel pending for another pass.

An actual profile-write failure keeps the in-memory collection and the existing storage warning while allowing an authorized remote backup. A later successful file write clears that warning. Confirmed cloud/relay operations never clear unrelated local storage failures. Deadlined operations cannot apply a late snapshot over newer practice or repopulate a signed-out/replaced account. The Nostr service propagates cancellation to its active transport task and retains its existing serialized signing/read/publish boundary.

This does not change the sharing default, award catalog, XP rules, session-only celebration queue, native backend configuration or membership grants. No Firebase/rules/Cloudflare deployment is required.

## Source and test evidence

`node scripts/export-achievement-retry.mjs` executes the actual `createRetrySync` with controlled timers and deferred completions. Ten traces cover 81 steps: coalescing, newer work during success/failure, pause/resume while in flight, startup without an existing job and the full backoff cap. Native public intent/timer/operation traces agree. Both generated outputs reproduce byte for byte. The source job, deadline, journal, status and integration hashes are retained in [the manifest](reference/achievement-retry-manifest.json); the exporter executes retrySync itself and reads the related integration sources for provenance.

- Core regression: 26 checks pass (1.382s), including original retry traces, award proof/catalog/queue behavior, first-run flags, onboarding and progress rebase contracts.
- Final6: 22 selected app checks complete with zero failures, including one explicitly skipped public live-relay read (2.865s). Six controller checks cover independent destinations, generation ownership, atomic intent restoration/current-account-only resumption, intent-write failure, deadline release and old-account completion. Eight AppModel checks use loopback relays: cloud-import failure with one authorized publication, lost relay acknowledgment without a second publication, disabled sharing, profile storage failure/recovery, intent-only failure, signed-out/account replacement and late cloud snapshots. Existing parser/signature/serialization/delivery/storage checks also pass. No public relay award is published by these tests.
- Final5: four real Firestore SDK checks pass (8.811s), covering once-only concurrent committed awards/quiet restoration, curriculum XP and receipt retries, first upload of offline work and historical XP staying off today's total. The complete selection has 25 checks, one skipped public live read and zero failures (11.565s). It uses a separately started, HTTP-healthy demo-project emulator on port 8330, stopped after validation. The final intent-only warning correction does not change Firebase service behavior.
- Final4: both actual app journeys pass (129.722s). The review award takes the Home fallback and Tutor footer, restores Tutor controls and remains collected after restart (61.561s). The lost-cloud-response journey starts from landing/onboarding, with twenty fixture XP and four committed flashcard-completion events. A real graded/rated six-XP review supplies event five through the production SDK verifier. A loopback gate drops the result **after the actual save commits**, across repeated retries and process restart. The collection remains at one of 76 with Sync pending. Opening the gate clears pending without new practice; XP stays at 26 across another restart and no celebration or public relay publication replays (68.161s). The final local-write fallback changes an error path not used by these healthy-file UI journeys.

The full app uses the same production recovery controller, Firebase service, Nostr service and screens. Debug-only fixture entry requires offline mode, an explicit delivery/retry opt-in, a UUID identity scope, a named demo Firestore database, validated local endpoints and the fixed demo project. The gate receives no learner data. It changes the return result after a real SDK commit; it does not inject an award, celebration, receipt or XP. Signing/publication checks use the loopback relay; ordinary and release launches retain their normal backend and relay configuration.

This checkpoint proves the stated recovery paths, not every loss boundary. A server commit whose transaction result never reaches the award-delivery hook, foreground local award evaluation, cross-process simultaneous writers, remote-signer dialog recovery, long offline periods, physical background suspension/storage exhaustion and broader interruption/localization/layout checks remain open. The simulator profile-write test uses a deliberately blocked path rather than exhausting device storage. The native atomic file is a platform adaptation of the browser localStorage/IndexedDB journal. The larger functional/design parity goal remains active.

Earlier attempts remain in `/tmp`. Build1 passes the existing eight app checks with one live-read skip; Core1 passes sixteen with the same skip. Final1 and Final2 pass their native selections, then fail against obsolete onboarding menu selectors; both runs are explicitly interrupted after the confirmed failure and terminate with code 73. UI3 reaches restart recovery but expects 6 total XP despite the Settings fixture's existing 20 XP. Emulator inspection confirms 26 XP, 6 daily XP and one six-XP review receipt. Final4 corrects the visible menu-row selection and asserts the initial 20 and final 26 XP. Final5 adds actual profile-write fallback and SDK regressions; Final6 distinguishes intent-only write failure from actual record-storage loss. No failed or interrupted full run is represented as passing.
