## Original sequence and native change

The actual `TeamView.loadData` awaits team and invitation records, exposes those cards, clears the global loading state, then supplies each creator's current in-memory row. It marks all teams' member progress loading and waits for the complete `Promise.allSettled` member batch. While pending, accepted-member slots without rows show skeleton cards. Final failure retains only a creator's local row; a failed joined team has null progress and shows the original member error text. An empty successful array and an undefined row state have separate empty/loading labels. Member failures log without an extra toast. An ordinary subscription update still retains previous rows on failure, as recorded in [TEAMS_STREAMED_ROSTERS.md](TEAMS_STREAMED_ROSTERS.md); initial batch failure has a different source outcome.

Native previously waited for signed roster, peer progress/profile queries and all legacy progress reads before returning any fresh roster. The new staged access callback publishes reconciled roster/invitation records and creator rows before member transport completes. The controller attaches known-team watches at that stage and releases global loading. It preserves prior noncreator rows until the final member batch settles. Later streamed roster/member results and live invitations retain their existing ownership/version fences over older full-read results. Closed or replaced account sessions reject both stage and final callbacks.

`NostrTeamsService.refreshRoster` verifies signed rosters and leaves without requesting progress/profile data. The following all-settled member phase retains existing verified public-row construction and starts independent private team reads concurrently with the public batch. Private reads use independent per-team snapshots, and failed reads cannot reuse another team's selected progress. Source-shaped pending/failure state is explicit on the snapshot; it does not change membership or action authority. Public actions continue using signed service records, and Firebase/Cloudflare services remain separate.

Native skeletons follow the original card hierarchy: 20-point 42%-width heading, three 58-point metrics, 14-point progress placeholder, 64-point companion circle and three text bars, original padding/margins and hidden accessibility semantics. Actual source CSS resolves skeleton colors to `#2f261d` → `#786654` in light mode and `#e5e7eb` → `#a3b4c9` in dark mode, with 0.7 opacity and a 0.8-second linear alternating pulse. Native uses those observed values. Frame captures compare layout, not phase-locked animation equivalence.
